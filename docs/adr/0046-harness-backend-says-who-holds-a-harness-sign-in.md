# The Harness backend says who holds a Harness sign-in token, in the Autonomous profile's shape

Status: accepted (2026-10-06). Built 2026-10-07 — the Harness backend's route and Google subject fill, the control plane's `off`/`shadow`/`primary` mode (default `off`), and the Harness CLI hand-off (held back until the cut-over); not yet deployed.

The control plane's (grid-apis) `/auth/harness` used to learn who holds a **Harness sign-in token** by presenting it to the Autonomous account API (`/me/profile`). Since 2026-10-01 Harness also grants sign-ins itself (a computer approved by QR), which Autonomous cannot read, and Harness plans to retire the browser sign-in that produced Autonomous tokens. So the control plane now asks the **Harness backend, and only it** (`GET /api/grid/profile`, bearer = the token), for every Harness sign-in token. The Harness backend answers in the subset of the Autonomous profile shape that `account_api.identity_from_profile` already reads, so the parser and every **account key** rule stay in the control plane, and the switch is a change of configuration, not of code: a mode (`GRID_HARNESS_PROFILE_MODE`, `off` → `shadow` → `primary`) chooses which upstream answers, and rollback is setting it back.

## Considered options

- **Two upstreams** — Autonomous tokens to the Autonomous API, Harness-issued ones to the Harness backend. Rejected: the control plane would have to tell token kinds apart and keep two integrations in step.
- **The Harness backend ports `identity_from_profile` and returns its own contract.** Rejected: the key rules are the control plane's invariants, not the Harness backend's — a `:` in a key bills the wrong wallet (the master charges `rsplit(":", 1)[-1]`), and an `autonomous-` prefix on a Google subject merges two key spaces. Porting them duplicates them where nobody owns them.
- **The Harness backend brokers the sign-in** with a service secret and passes the session token back. Rejected: Grid credentials would travel through Harness, and the secret could mint a session for any account.
- **A signed assertion verified offline (JWKS).** Rejected for now: key management and rotation for one call per sign-in.
- **Trading a Harness-issued sign-in for an Autonomous token.** Impossible: the Autonomous account service has no grant for it.

## Consequences

- **The envelope is a contract, not an accident.** `status: 1` (an integer, not Harness's usual `{success, data}`), `data.id`, `data.email`, `data.full_name` and `data.customer_socials[{source, uid}]` must not be "tidied" on either side; a fixture shared by both repositories pins it. The Harness backend copies only these fields — never the profile body, whose `customer_socials[].token` is the person's live Google OAuth token.
- **Only computer sign-ins and Autonomous tokens are answered.** A phone sign-in is refused: no phone calls Grid, and a phone sign-in cannot mint a hand-off code. ⚠️ It CAN approve a computer's QR sign-in (pre-existing, `routes/qrSignIn.ts`), and the computer sign-in that mints is answered — so a lost phone is still one step from a Grid session. Recorded on ticket 01 for a decision; not changed by this work.
- **The Google subject of a Harness-issued sign-in is what the Harness backend last read live** from an Autonomous token of the same account (every successful read overwrites it, including to "none"; rechecked after 7 days). When it has never read one, the sign-in is **refused rather than keyed** — an account key is permanent, and guessing `autonomous-<id>` for a Google-linked account would split it from its website sign-in for good.
- **"Not yet known" is a status, not a code.** On `/api/grid/profile` the Harness backend answers **409** for that case and nothing else, and the control plane branches on the status alone — no machine-read refusal code is introduced (the public `grid` CLI alone parses six, and keeping that count low is a contract). It answers the caller 409 with a sentence naming the way forward (sign in to Harness once with Google, Apple or email on any device); the `grid` CLI shows every non-404 refusal verbatim, so nothing changes there.
- **Every refusal names the service that answered** — Harness for the Harness backend, Autonomous for the Autonomous API during the shadow — because who to blame is what these sentences exist to say.
- **Cut over behind a shadow comparison on PROD:** both upstreams are asked for Autonomous tokens (`GRID_ACCOUNT_API_BASE_URL` and a new `GRID_HARNESS_PROFILE_URL`, side by side until the cut) and the Autonomous answer is used, until at least 3 days and 50 compared sign-ins show no difference. Each comparison is one WARNING line (`harness shadow: same` / `differs (fields: …)`, field names only; or `harness failed (…)`, `not compared (busy)`, and `answered by harness (autonomous HTTP 401)` when there was no comparison) — WARNING because production uvicorn runs without a log config and nothing quieter reaches the journal. Only `same` and `differs` count toward the criterion; `harness failed` lines are read, not counted. The Harness CLI stops refusing Harness-issued sign-ins only after that shadow **and** the Harness backend's stored-versus-live Google subject check are both clean.
- **It assumes every account has at least one sign-in made through the Autonomous account service** — true today, and still true under Harness's mobile-first plan, whose first device signs in on an Autonomous emailed code. "Not yet known" is then rare and temporary: right after a deploy until one of the account's Autonomous-signed devices is seen, after a failed read until the next one, or — the only lasting case — an account all of whose Autonomous-signed devices were gone before the deploy, which the refusal's sentence resolves. If Harness ever signs a first device in without Autonomous, neither the Google subject nor the customer id can be learned any more, and how the control plane chooses an account key has to be revisited.
- **Revoking a device in Harness does not end its Grid session** — a session token can only be revoked account-wide. Accepted; tracked separately.
